## Explícitamente NO pendiente (ya decidido, no volver a abrir)

Reglas de negocio: relación contrato→préstamo (1:1), aplicación cronológica de pagos, cálculo de mora derivado, flujo de refinanciación, categorías de gasto, motivos de intento fallido, matriz de permisos por rol, estados de suscripción (incluido `ARCHIVADA` vs `SUSPENDIDA`), prioridad de tickets (sin SLA), fórmula de proyección de cobros futuros.

Política de contraseñas (8+ caracteres con letra y dígito, ADR 0004), estados de Negocio y Suscripción (dos campos sincronizados, `PROXIMA_A_VENCER`/`VENCIDA` derivados, vencimiento por calendario con ajuste de fin de mes, ver 02 §1.2–1.3), unicidad global del nombre de usuario (02 §1.4), zona horaria por negocio (02 §1.2; ADR 0003).

Cerrado en F1 (ADR 0005): resultado de la auditoría (`OK`/`RECHAZADO`, y solo cuando el actor autenticado carece de permiso sobre esa entidad; visibilidad por rol en 02 §8), re-suscripción de un negocio archivado (suscripción nueva, la `ARCHIVADA` queda como historial) y restablecimiento de contraseña por el Super Admin (solo la cuenta `ADMIN_NEGOCIO` en V1, con el evento `ContrasenaRestablecida`).

Decisiones técnicas: stack (`03-ARQUITECTURA.md`), retención de backups (7 días), moneda (COP sin decimales), formato de identificadores (UUID interno + código legible de contrato asignado al confirmar), seguridad de Super Admin (mismo flujo Supabase Auth que los demás roles, sin 2FA en V1), umbral de `PROXIMA_A_VENCER` (5 días antes del vencimiento), transacciones con `pg` directo (ADR 0001), 1 usuario = 1 negocio con email sintético (ADR 0002), interés en puntos básicos con redondeo half-up, jornada bloqueante sin cobros ni gastos fuera de una jornada `ABIERTA` (02 §5.2, invariante 13), movimientos de caja siempre definitivos, saldo de Caja Mayor nunca negativo, un solo saldo de apertura por negocio y ajuste ± / reverso total (ADR 0006).

Todo esto ya está en `02-DOMINIO.md` / `03-ARQUITECTURA.md` — si Claude Code encuentra ambigüedad en alguno de estos puntos durante la implementación, es que el documento correspondiente quedó incompleto, no que la decisión siga abierta. En ese caso se corrige el documento, no se inventa en el código.

### Patrones explícitamente rechazados (no reintroducirlos como "mejora")

Recogidos aquí porque varias skills y guías externas los recomiendan como buenas prácticas. Ninguno es un requisito abierto: son **rechazados**, y proponerlos de nuevo cuenta como error, no como iniciativa.

- **SWR / caché de cliente para saldos.** `03-ARQUITECTURA.md:110` prohíbe el estado global para datos financieros y exige que cada pantalla consulte datos frescos tras un comando exitoso. El repo revalida con `router.refresh()` después de cada comando; SWR cachearía y serviría **un saldo viejo justo después de registrar un pago**, que es el peor momento posible para equivocarse de cifra.
- **`after()` de Next.js para la auditoría.** `03-ARQUITECTURA.md:70` exige que el evento de auditoría se cree **dentro** de la transacción PostgreSQL (`03-ARQUITECTURA.md:99`: la auditoría es un hecho inmutable y atómico con el comando). `after()` corre aunque la respuesta haya fallado: produce auditoría huérfana de acciones que nunca ocurrieron.
- **Server Actions.** El patrón obligatorio de `03-ARQUITECTURA.md` §3 (líneas 59-72) empieza en **Route Handler** → validar → servicio → una transacción. El repo no usa Server Actions; sustituirlas cambiaría el contrato de CSRF (`assertSameOrigin`), el manejo de errores (`errorResponse`) y el alcance del `requireSession()`.
- **Paralelismo por declaración** (`better-all`, ejecutar escrituras concurrentemente). `03-ARQUITECTURA.md:81` exige tomar los bloqueos *"siempre en el mismo orden para evitar interbloqueos"*. Una abstracción que maximiza el paralelismo borra ese orden explícito, que es justo lo que hace auditable el contrato de bloqueo.
- **Redis o cualquier caché distribuida.** `03-ARQUITECTURA.md:21` lo prohíbe por nombre en la lista de dependencias (y `:5` lo repite al fijar el stack): no se añade sin necesidad real demostrada.
- **Caché de lecturas con LRU entre peticiones.** `03-ARQUITECTURA.md:88`: *"Las funciones que escriben dinero no usan caché"*. La prohibición cubre el **espíritu**, no solo la escritura: un saldo o una cuota cacheados entre peticiones son un saldo o una cuota viejo.
- **`Intl.NumberFormat` (u otra API dependiente de ICU) para formatear dinero.** `src/shared/money/money.ts:51` lo dice literal: *"Agrupación manual: no depende de datos ICU"*. Es deliberado: V1 es COP sin decimales y el formateo no puede depender de los datos de configuración regional del sistema donde corre el servidor ni del locale del navegador.
